## 0. 先看结论

- **一个项目从立项到上线通常涉及 7 类角色**：产品经理、数据科学家、软件工程师、设计师（UI/UX）、运维工程师、市场宣传、客户支持。大模型时代，这些角色里大量**文书类工作**（含写代码）可以被接管，一个人交付成为可能；
- **最吃力的三个角色有明确的降负路径**：设计师 → 直接用 Gradio / Streamlit 复用现成交互，不造轮子；运维 → 容器化部署（Docker），Dockerfile 一次构建多处运行；数据科学家 → Agent 场景下底层大模型已经干了绝大部分，第一个项目几乎不需要训练模型；
- **大模型能深度参与的 7 个阶段**：市场调研 → 竞品分析 → 产品设计初期 → 文档与报告 → 用户反馈 → 宣传推广 → 线上迭代。**开发测试到上线前重点在前四个**；
- **本课最有价值的部分是"怎么问"**：用英文提问、要求表格化输出、在提示词里显式写"联网查询"、把需求拆成可并行的多条任务——以及一个容易被忽略的细节：**不要让模型在同一次对话里做翻译**，那不增加信息量却会挤占上下文窗口。

## 1. 一个人做一款 Agent：7 个角色的工作量

课程假设学习者是"有工作经验、但一个人 solo 做项目"的状态，因此**跟线上运营、售后相关的工作量可以先放一放**，聚焦项目前期 + 研发 + 上线。

| 角色 | 主要职责 | 一个人做时的现实情况 |
| --- | --- | --- |
| **产品经理（PM）** | 定产品要不要做、向上汇报、市场调研、跨团队收集信息；做计划、定义**用户故事 / 核心功能 / 版本划分** | 早期最好先定义出 **MVP**——价值能体现、技术上没有无法逾越的难关，才有可能像滚雪球一样持续拿到资源 |
| **数据科学家** | 训练模型、部署模型（深度学习时代的核心角色） | **Agent 场景下工作量大幅缩水**：数据的收集、消化、处理、判断下一步动作，全由底层大模型承担，课程说"大模型帮我们做了 90% 以上"。做第一个项目（开源哨兵 / 信息检索工具）时这部分几乎可忽略 |
| **软件工程师** | 开发维护前端、后端、业务逻辑、对接大模型的代码 | 工作量主体。除 OpenAI API 外，还有 **LangChain** 可对接各类模型（含私有化模型）；后续 **Ollama** 私有化部署也主要落在这个角色 |
| **设计师（UI / UX / UED）** | 提升交互体验、降低使用门槛 | **研发 solo 时最痛苦的部分**——大部分研发没有审美 / 美术训练。对策：直接用 **Gradio / Streamlit** 这类现成工具，**极大程度复用框架自带的交互方式，不要自己造轮子**。不像 React 前端还要满足 UED 的各种定制需求，Agent 的用户故事相对简单，够用了 |
| **运维工程师** | 保障线上稳定 | 典型困境：**不出事没人记得有这个人，一出事背锅的总是他**。对策：**用容器化方式部署**——Docker 生态里大量面向运维 / 稳定性 / 自动拉起的能力，Dockerfile 一次构建可在多环境运行。没有 Docker / Compose 经验的话，跟 ChatGPT 交流学新技术比啃文档快 |
| **市场 / 宣传** | 产品宣传、软文投放 | 课程最后一节会实操：把开源项目在海内外平台生成宣传材料发布。研发同学普遍不擅长，但大模型能生成内容，自己只需注册账号去试 |
| **客户支持** | 用户反馈、问题解决 | 用户投诉越来越不走工单，直接在社交媒体吐槽；**舆情监控 + 用户反馈分析用大模型来做是常见手段** |

> 一句值得记的话：课程认为**写代码本身也属于文书类工作**——"代码也只是文字，只不过是计算机能看得懂的文字"。

## 2. 大模型能接管的 7 个阶段

把各角色里的文书类工作按阶段拆开：

```text
1. 市场调研       → 我做的这个 Agent 到底有没有需求？需要量化数据支撑
2. 竞争对手分析   → 有没有人已经做了类似的工具？
3. 产品设计初期   → 定义核心功能；找研发负责人要一个 demo，评估做成产品级还要多少人天
4. 文档与报告     → 技术文档、用户手册（国内外普遍写得不好，但代码既然是它写的，顺手写份文档完全可行）
5. 用户反馈       → 收集表单、社交媒体评论
6. 宣传推广       → 生成宣传内容
7. 线上问题解决与迭代 → case by case，同样可以跟大模型结对
```

- 前三个阶段在真实公司里是**标准立项流程**：PM 有 idea → 找研发负责人 → "核心功能不超过三个，今天或这周给我个 demo，再告诉我做成产品级还要多少人天"；
- 阶段 4 的现实依据：课程整个第一个 Agent 的代码**90% 以上由 GPT-4 直接写出**，人只做小部分调整；
- 阶段 5-7 的获取途径：线上表单，或直接从小红书 / Twitter 等内容平台的评论里抓取，再用大模型做分析。

**开发测试到上线之前，重点放在前四个阶段。**

## 3. 实战：用 ChatGPT 完成立项早期工作

课程打开了一段真实的 ChatGPT 对话（右上角 Share 生成只读分享链接）逐段讲解。

### 3.1 提示词设计的几个可复用技巧

| 技巧 | 做法 | 原因 |
| --- | --- | --- |
| **用英文提问** | 提问尽可能用英文，模型反馈通常更好 | 课程明确说的经验结论 |
| **翻译要"捞出去"** | 不想读大段英文时，**把回复复制到另一个窗口翻译**，不要让它在当前对话流里翻译 | 在同一对话里翻译**不增加任何信息量**，却占用上下文窗口；窗口一旦超限就会被压缩，而中英文内容是**完全冗余**的，压缩时纯属浪费 |
| **指定输出格式** | 明确要求"以**表格**形式呈现数据分析结果" | 模型默认只会**分点陈列**；要说服 leader / TL 就必须有量化结果 |
| **角色 + 阶段设定** | "你是一个 **startup coach**，我现在处于**立项早期阶段**" | 把模型锚定在"这项目值不值得做"而不是"怎么实现" |
| **要求两类产出** | 同时要 **macro strategy（宏观战略）** 和 **practical guidance（实操指导）** | 战略用于说服，实操用于落地 |
| **显式声明联网** | 把"**联网查询**"写在提示词**前面** | GPT-4 / GPT-4o 等都支持联网，但需要明确触发 |

### 3.2 ChatGPT 给出的战略建议

**目标设定——关注什么信息**（对不了解 GitHub 开源生态的 PM 尤其有用）：

- **不能只看 feature，还要看 issue**：新版本发了几个、有哪些 **open issue**、新发布的特性引出了哪些新问题、哪些 bug 一直没被解决。课程特别肯定了这一点——很多团队引入开源项目时只关注特性，不花精力看"这些特性有哪些 bug 一直没解决"；
- **Pull Request（PR）** 合并了哪些新代码；
- 项目的 **roadmap（路线图）**。

**目标用户**：

- 不只是 developer，**投资人**也是关键用户——红杉、**a16z** 等美国一线投资机构越来越多地投以开源社区 / 开源项目为主体的公司。典型：**LangChain 最近一轮融了 2500 万美金**（已查证：Series A，Sequoia 领投，2024-02），**Hugging Face 最近一轮 2 亿美金**（查证为 2.35 亿美元 D 轮，2023-08）；
- **技术爱好者 / 非开发者用户**：典型如 **Stable Diffusion**，大量非开发者用户根本不写代码，只是在它用 **Gradio** 做的控制面板上研究什么参数能出什么效果。

**如何判断"高影响力项目"**（PM 不知道研发关注什么项目时的抓手）：

- GitHub 维度：**star 数、fork 数、活跃度**（最近一次提交是 1 小时前 / 1 天前 / 10 天前）；
- **技术类别与 GitHub trending、主流技术社区的相关性**——判断这项技术是不是已经被慢慢淘汰了。课程举的反例：云计算领域的 **Hadoop** 已经不热了，**Spark** 也慢慢不再是最热的技术。

### 3.3 ChatGPT 给出的实操建议

| 环节 | 建议 | 备注 |
| --- | --- | --- |
| **抓数据** | **GitHub API**；或爬虫框架 **BeautifulSoup**（Python，非常好用） | 收集信息是这个产品的第一步 |
| **数据处理** | NLP 基础工具；**Transformers**（Hugging Face 开源） | 这一轮还没让模型介入，仍用传统工具 |
| **存储与调度** | **Airflow** | 2018 年深度学习开源热潮中的知名项目，用来调度各种 ML 工作流 |
| **深度集成** | 与 GitHub 无缝集成，GitHub 本身提供大量 **Webhooks** | 这是 PM 定完需求后要跟研发规划路线图时考虑的问题 |
| **扩展性** | 不局限于一种信息渠道和类型——金融领域、新闻领域都能变成订阅器 | 课程明确要求第一个项目要有强扩展性，这跟后面要聊的某个竞品思路非常类似 |
| **通知系统** | 邮件在国内不是每天查看；**Slack** 在国内也不常见，更多是**企业微信 / 钉钉** | 这类**本地化差异是 ChatGPT 一开始考虑不全的**，需要入乡随俗调整，但框架本身很有价值 |
| **安全合规** | **GDPR**（欧盟） | 应用开发实战部分已深度剖析过 |

> 课程评价：这套建议"已经非常全了，要启动这个项目，该有的信息框架都够了"。

## 4. 与研发负责人沟通：让模型把版本和排期"排版"出来

带着上面那套信息去找研发负责人，如果对方比较忙或风格上需要完善的需求，更好的做法是**直接让 ChatGPT 把功能拆成三个版本，并捋出各版本的产品特性与研发计划**。

| 版本 | 产品特性 | 说明 |
| --- | --- | --- |
| **V1 基础功能** | 数据收集与存储、用户界面、通知系统 | 很初级：能筛选出一批项目，把**项目级信息**存下来，配一个简单仪表盘 |
| **V2 高级数据处理** | 更细的**项目内部数据**爬虫、分析与总结；展示层支持搜索过滤 | 数据处理深一层，展示层开始可交互 |
| **V3 扩展与集成** | 集成 **Webhook**；支持更多数据来源（不只爬 GitHub repo，还能爬**项目官网**、项目 **docs 文档**）；用户界面更友好 | 对应 3.3 里的扩展性要求 |

**这段最重要的经验不是版本怎么分，而是"排期必须人工矫正"**：

- ChatGPT 给的研发计划是**每个版本 3 个月**，三个版本 9 个月——课程吐槽"真的是非常 chill，跟湾区程序员比较像"；而实际上整个 Agent 按课程进度**不到一个月**就能做完；
- 让模型改成一个月，**矫正了两次**才改对——它仍然按每版三个月排布，"没有理解到位"；
- 课程对模型表现的分析：这次**没有使用最强的 GPT-4**，印象中是 GPT-4o mini。没充 Plus 的话聊着聊着就可能降级到免费的 GPT-4o mini，这种情况会发生，**但不必因此对它的完整性失望，多轮交流可以改善**；
- 版本号命名（V1/V2/V3）这类细节也都可以继续让模型调整。

**推荐的沟通节奏**：先把功能跟模型捋细 → 让模型排出分版本的产品特性与研发计划（课程称之为"排版"）→ 排完版再跟 TL 沟通。solo 就是自己跟自己沟通；两到三人的小团队就由 PM 去跟研发负责人沟通。

## 5. 第一周研发计划：两条线并行

定完版本之后还有一件事要**向上管理**：这事儿到底有没有价值、有没有竞争对手。这条线**平行于**跟 TL 的沟通，需要单独准备策略。

课程的第一周计划是**同时给模型两个并行任务**：

1. **市场调研 + 竞争分析**：用"联网查询"提示词要求它收集分析市场数据、产出竞争对手分析报告。它搜出了 **GPT Researcher**、**MetaGPT**、**SuperAGI**，以及一些 "AI in market research" 的项目，一共扫了五大类网站，从不同站点各取信息——课程说这个过程"有点像我们之前用某个工具实现 Agent 联网时做的工作"，只不过 ChatGPT 已经把联网内置进业务流程，直接下提示词就行，不用自己调 Agent 代码；
2. **搭建基础架构代码**：指定 **Python 3.10 及以上**（考虑到有人可能连 Python 都没装）、用 **virtualenv** 做虚拟环境管理、给出项目结构。它生成的基础代码包含 **data collector** 数据收集模块，数据库选 **PostgreSQL**（开源社区友好，且 **PostgreSQL 也支持向量数据库的形式**）。

**这同时也是一次长对话记忆测试**——在很长的对话里，模型还能不能记住之前排的研发计划。结果：**能**，它记得第二周还要继续做数据收集。

课程强调：以上全部是用**免费的 ChatGPT** 就能拿到的能力，因为这类工作本质上属于**信息检索 + 文书生成**。
